Professional Self-Assessment

Completing the Computer Science program has changed the way I approach technology and problem-solving. Earlier in the program, I tended to look at programming as a collection of individual concepts and assignments. As I progressed through courses involving software development, data structures and algorithms, databases, testing, full-stack development, security, and system design, I began to understand how those concepts work together in a complete software solution. Developing this ePortfolio gave me the opportunity to look back at that progression and demonstrate how my approach has changed from simply creating software that works to developing solutions that are maintainable, efficient, secure, testable, and understandable to others.

My professional goal is to transition my technical education and existing professional experience into a career in software development or a related computer science field. My current work as a service advisor has helped develop skills that transfer directly into a technical environment. I regularly listen to customers describe problems, document technical information, coordinate with technicians, prioritize work, and explain solutions to people with different levels of technical knowledge. Software development involves many of the same communication and problem-solving skills. A developer must understand what a user or stakeholder needs, translate those needs into technical requirements, work with others to implement a solution, and explain the results clearly. Combining those professional skills with the technical knowledge I developed throughout the Computer Science program has better prepared me to work with both technical and nontechnical audiences.

My coursework has also strengthened my ability to communicate technical information to stakeholders. Data structures and algorithms are another area where my thinking has developed significantly. I learned that producing the correct output is only one part of solving a computing problem. The way data is stored, searched, sorted, and processed can have a significant effect on the efficiency and scalability of a solution. Understanding concepts such as algorithmic complexity has helped me evaluate the trade-offs involved in choosing one approach over another. For example, selecting a HashMap for identifier-based retrieval can provide average constant-time, O(1), lookup compared with the O(n) search that may be required when scanning a simple list. At the same time, using a HashMap introduces other considerations when ordered output is needed, which may require creating and sorting a separate view of the data. Learning to consider these trade-offs has helped me move beyond asking whether a solution works and toward asking whether it is an appropriate solution for the problem being solved.

Software Design and Engineering

This enhancement focuses on improving the organization, maintainability, testability, and reliability of the Contact Service application. The original project was refactored into separate model, validation, repository, and service components. The enhanced version also includes dependency injection, logging, stronger validation, clearer documentation, and expanded JUnit testing.

Artifact Description

The artifact I selected is the Contact Service application that I originally created in CS 320: Software Testing, Automation, and Quality Assurance. The project was created in Java and uses JUnit 5 tests to verify that contact records meet the required specifications. The original application allowed users to add, update, and delete contacts while validating the contact ID, first name, last name, phone number, and address.

I selected this artifact because it provided a good foundation for demonstrating software design and engineering skills. The original project worked correctly, but its structure was simple and placed several responsibilities within only a few classes. This made it a strong candidate for refactoring into a more organized and maintainable application.

Justification and Improvements

I included this artifact in my ePortfolio because it demonstrates my ability to improve an existing software application without removing its original functionality. The enhanced version shows skills in object-oriented design, code organization, validation, testing, logging, and separation of responsibilities.

The original Contact class stored contact data and also contained all of the validation rules. The ContactService class handled business operations while directly managing the in-memory collection used to store contacts. Although this design worked for a small project, it would become harder to maintain as additional features were added.

I improved the project by organizing the application into model, validation, repository, and service packages. The Contact class now focuses on representing a contact record. The ContactValidator class centralizes the validation rules so they can be reused consistently throughout the application. The ContactRepository class manages the in-memory storage of contact records, while the ContactService class handles business operations such as adding, updating, deleting, and retrieving contacts.

I also added constructor-based dependency injection to the service layer. This allows the ContactService to receive a repository instead of creating all dependencies internally. This improves testability and makes it easier to replace the in-memory repository with a different storage method in the future.

Logging was added to record successful operations, duplicate contact attempts, missing contact operations, and invalid null inputs. The logging avoids displaying sensitive contact information such as names, phone numbers, and addresses. I also strengthened phone number validation so that a phone number must contain exactly 10 numerical digits instead of only checking its length.

The JUnit test suite was expanded from 7 tests to 38 tests. Additional tests now cover duplicate contacts, null inputs, partial updates, missing contacts, repository operations, dependency injection, and each validation rule. All 38 tests pass with no errors or failures.

Course Outcome Coverage

This enhancement made substantial progress toward the course outcome involving the use of well-founded techniques, skills, and tools to implement computing solutions that deliver value. The layered package structure, centralized validation, repository pattern, dependency injection, logging, and expanded testing demonstrate software engineering practices that improve maintainability and reliability.

The enhancement also supports the communication outcome. The code includes clearer class names, method names, package organization, documentation, and test descriptions. These improvements make the project easier for another developer to understand and maintain.

The project also demonstrates progress toward developing a security mindset. Input validation prevents invalid contact data from being stored, and the logging avoids exposing unnecessary personal information. The service also rejects null values in important operations and provides controlled exception messages.

My original outcome-coverage plan remains mostly unchanged. The software design and engineering outcome is the main focus of this enhancement. The algorithms and data structures outcome is addressed more directly in the next enhancement, and the database outcome is addressed when persistent storage is added.

Reflection

Enhancing this artifact helped me understand the difference between code that works and code that is designed for long-term maintenance. The original project met its basic requirements, but it combined data storage, validation, and business operations too closely. Separating these responsibilities made the project easier to understand and created a clearer structure for future expansion.

One challenge was moving classes from the default package into named packages. Java classes inside named packages cannot import classes from the default package, so the Contact model and ContactService had to be moved carefully. Eclipse refactoring tools helped update the necessary imports and references.

Another challenge was preserving the original functionality while changing the internal design. I ran the JUnit tests after each major modification to make sure the project continued to work correctly. This showed me the importance of automated tests during refactoring. The tests provided immediate feedback and made it safer to reorganize the code.

I also learned that code coverage percentages can be affected by the project structure. Because the test classes and application classes are stored in the same source folder, Eclipse includes the test code in the overall coverage calculation. Even though the percentage changed as new tests were added, the expanded suite still provided much more complete testing of the application behavior.

Overall, this enhancement improved the professionalism, organization, testability, and maintainability of the Contact Service application. It also prepared the project for the later enhancements involving data structures and database persistence.

Algorithms and Data Structures

This enhancement improves the efficiency and flexibility of the Contact Service application. Contact records are stored in a HashMap using the contact ID as the key, allowing average O(1) lookup, insertion, updating, and deletion. When alphabetical output is needed, the application copies the contacts into an ArrayList and sorts them by last name and then first name using a Comparator.

Artifact Description

The artifact selected for this enhancement is the Contact Service application originally created in CS 320: Software Testing, Automation, and Quality Assurance. The Java application allows users to add, update, delete, and retrieve contact records while validating the contact ID, first name, last name, phone number, and address.

I continued using this artifact because its model, validation, repository, and service structure provided a strong foundation for demonstrating algorithms and data structures. The storage logic could be improved without rewriting the rest of the application.

Justification and Improvements

I included this enhancement in my ePortfolio because it demonstrates my ability to select a data structure based on how an application accesses its information. Contacts are normally added, retrieved, updated, or deleted using a unique contact ID. For that reason, I used a HashMap with the contact ID as the key and the Contact object as the value.

The HashMap provides average O(1) lookup, insertion, and deletion. A list-based approach would generally require an O(n) sequential search to locate a contact by ID. The HashMap also allows duplicate IDs to be detected efficiently by checking whether the requested key already exists.

Because a HashMap does not maintain alphabetical order, I added a separate sorting algorithm for displaying contacts by name. The repository copies the stored contacts into an ArrayList and sorts them with a Comparator. Contacts are ordered first by last name and then by first name when two contacts have the same last name. Creating the list requires O(n) time, while sorting requires approximately O(n log n) time.

This design preserves efficient ID-based operations while still providing ordered output when needed. The sorting feature is exposed through the ContactService so callers do not need to access the repository directly.

The JUnit test suite was expanded from 38 tests to 45 tests. New tests verify sorting by last name, first-name tie-breaking, empty repository behavior, and confirmation that producing a sorted list does not alter the stored contacts. All 45 tests pass, and the Eclipse coverage report shows 94.4% overall instruction coverage.

Course Outcome Coverage

This enhancement addresses the course outcome involving the design and evaluation of computing solutions using algorithmic principles and appropriate trade-offs. I evaluated how contacts are accessed, selected a HashMap for efficient ID-based operations, and added a separate sorting algorithm for alphabetical output.

The enhancement also demonstrates the use of well-founded computing techniques and tools, including Java collections, generics, ArrayList, Comparator, method references, layered design, JUnit 5, and Eclipse code coverage. The narrative, documentation, method names, and test descriptions also support professional technical communication.

The algorithms and data structures outcome is the main focus of this enhancement. The repository and service layers also support the software design and engineering outcome. This work provided the foundation for the later database enhancement, which added SQLite persistence while preserving the service behavior developed during the first two enhancements.

Reflection

This enhancement helped me understand that choosing a data structure depends on the operations an application performs most often. A list may be appropriate for a small project, but searching by ID becomes less efficient as the number of contacts increases. The HashMap creates a direct relationship between the contact ID and the stored Contact object.

The main trade-off was that the HashMap does not keep contacts in alphabetical order. Instead of replacing it with a structure that would make ID access less direct, I kept the HashMap and created a separately sorted view. This demonstrated how multiple data structures and algorithms can work together to meet different requirements.

One challenge was ensuring that this milestone demonstrated additional algorithmic work because the repository already used a HashMap after the previous enhancement. Adding the Comparator-based sorted view, exposing it through the service layer, documenting time complexity, and expanding the tests made the algorithms and data structures enhancement more complete.

Overall, this enhancement improved the efficiency, flexibility, and professionalism of the Contact Service application. It demonstrates my ability to evaluate access patterns, select an appropriate data structure, implement sorting logic, explain complexity trade-offs, and verify the results with automated testing.

Databases

The database enhancement adds SQLite persistence to the Contact Service application. Contact information is stored in a relational database and remains available after the application closes. Parameterized SQL statements are used to support secure create, read, update, and delete operations.
