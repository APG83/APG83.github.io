Artifact Description

The artifact I selected is the Contact Service application that I originally created in CS 320: Software Testing, Automation, and Quality Assurance. The project was created in Java and uses JUnit 5 tests to verify that contact records meet the required specifications. The original application allowed users to add, update, and delete contacts while validating the contact ID, first name, last name, phone number, and address.

I selected this artifact because it provided a good foundation for demonstrating software design and engineering skills. The original project worked correctly, but its structure was simple and placed several responsibilities within only a few classes. This made it a strong candidate for refactoring into a more organized and maintainable application.

Justification and Improvements

I included this artifact in my ePortfolio because it demonstrates my ability to improve an existing software application without removing its original functionality. The enhanced version shows skills in object-oriented design, code organization, validation, testing, logging, and separation of responsibilities.

The original Contact class stored contact data and also contained all of the validation rules. The ContactService class handled business operations while directly managing the in-memory collection used to store contacts. Although this design worked for a small project, it would become harder to maintain as additional features were added.

I improved the project by organizing the application into model, validation, repository, and service packages. The Contact class now focuses on representing a contact record. The ContactValidator class centralizes the validation rules so they can be reused consistently throughout the application. The ContactRepository class manages the in-memory storage of contact records, while the ContactService class handles business operations such as adding, updating, deleting, and retrieving contacts.

I also added constructor-based dependency injection to the service layer. This allows the ContactService to receive a repository instead of creating all dependencies internally. This improves testability and makes it easier to replace the in-memory repository with a different storage method in the future.

Logging was added to record successful operations, duplicate contact attempts, missing contact operations, and invalid null inputs. The logging avoids displaying sensitive contact information such as names, phone numbers, and addresses. I also strengthened phone number validation so that a phone number must contain exactly 10 numerical digits instead of only checking its length.

The JUnit test suite was expanded from 7 tests to 38 tests. Additional tests now cover duplicate contacts, null inputs, partial updates, missing contacts, repository operations, dependency injection, and each validation rule. All 38 tests pass with no errors or failures.

Reflection

Enhancing this artifact helped me understand the difference between code that works and code that is designed for long-term maintenance. The original project met its basic requirements, but it combined data storage, validation, and business operations too closely. Separating these responsibilities made the project easier to understand and created a clearer structure for future expansion.

One challenge was moving classes from the default package into named packages. Java classes inside named packages cannot import classes from the default package, so the Contact model and ContactService had to be moved carefully. Eclipse refactoring tools helped update the necessary imports and references.

Another challenge was preserving the original functionality while changing the internal design. I ran the JUnit tests after each major modification to make sure the project continued to work correctly. This showed me the importance of automated tests during refactoring. The tests provided immediate feedback and made it safer to reorganize the code.

I also learned that code coverage percentages can be affected by the project structure. Because the test classes and application classes are stored in the same source folder, Eclipse includes the test code in the overall coverage calculation. Even though the percentage changed as new tests were added, the expanded suite still provided much more complete testing of the application behavior.

Overall, this enhancement improved the professionalism, organization, testability, and maintainability of the Contact Service application. It also prepared the project for the later enhancements involving data structures and database persistence.

Algorithms and Data Structures

This enhancement improves the efficiency and flexibility of the Contact Service application. Contact records are stored in a HashMap using the contact ID as the key, allowing average O(1) lookup, insertion, updating, and deletion. When alphabetical output is needed, the application copies the contacts into an ArrayList and sorts them by last name and then first name using a Comparator.

Databases

The database enhancement adds SQLite persistence to the Contact Service application. Contact information is stored in a relational database and remains available after the application closes. Parameterized SQL statements are used to support secure create, read, update, and delete operations.
